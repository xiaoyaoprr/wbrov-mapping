# 无 Tag 连续建图：候选修复与验证边界

用户本轮澄清的目标是减少无 Tag 建图过程中的中断，不是要求操作员等停图后再找 Tag。当前生产 8 号仍为 `mapping_combo42_camera6`；本轮修改在 `codex/round6-capture-recovery` 和独立 Jetson 候选环境，尚未部署。

## 已修改

1. **正常续建不再额外套用恢复门槛。** `DeferredMappingSession` 原先无论是否已获准写主图，都先调用 `localGeometryReady()`。后者要求恢复级证据，包括更高的内点比例；正常质量已合格的帧也可能被挡住。新增 `frameProcessingReady()`：同一已注册坐标系、主图写入授权仍有效时，使用正常质量要求；初始化、暂停、丢失、过期、坐标系改变仍走原有恢复检查。未降低正常质量、恢复质量、几何验收、点云密度或处理帧数。
2. **减少录制段的重复同步。** 每段保留数据文件 fsync、回执文件 fsync、覆盖两次重命名的一次目录 fsync。正在录制的进度状态在上述三步成功后原子替换，不再额外 fsync 文件和目录；启动、最终关闭、失败状态仍持久化。每段同步调用从 5 次降到 3 次。未改成超时丢帧，也未增加队列容量。
3. **记录直接可查的停止原因。** `frames.csv` 增加完整 `quality_reason` 及运动、尺寸、协方差、视觉、深度、恢复级质量字段。状态 JSON 保留当前和最近失败的质量证据、两条恢复通道各自的理由、旧帧配准计数和对应源时间。
4. **区分无 Tag 与不能建图。** HUD 显示主图 Tag 数为 0 时仍可尝试旧关键帧恢复；检测数不等于绑定数，绑定节点数不等于独立参考数。显示所有已验证 Tag 参考数，未核验的数据不冒充零。正常建图不要求 Tag；Tag 通道失败后依然尝试原有纯视觉通道。
5. **区分文件同步与线程调度。** 每段 `seal_latency.jsonl` 分别记录 flush、数据 fsync、重命名、回执写入/fsync、目录 fsync，以及队列积压、生产者等待、写线程 CPU/运行队列等待、Dirty/Writeback。设备没有 `/proc/pressure/io` 时明确标记 unavailable，不把缺失解释成无 I/O 压力。
6. **将逐帧写文件与段持久化分到两个线程。** 候选 3 中，前者继续按源时间顺序压缩、写入 `.partial` 文件，后者串行完成数据/回执/目录同步；只有完成持久化后才提升 `sealed_segments`。待持久化队列只存路径对应的段元数据，同时限制为 32 段、512 MiB（包含正在同步的段），原始帧队列仍为 64 帧。最终关闭必须排空两个线程；任何错误都保留未完成数据并报告失败。超过容量仍会施加反压，不承诺任意长磁盘故障下无损且永不阻塞。

## 当前证据与限制

正常续建的额外拦截由状态机回归复现并验证修复。但第一版三组完整录像回放中，没有发现 `main_write=1, usable=1, recovery_geometry=0` 的帧；**不能把这一修复说成此前现场停图的已证实主因**。

本轮重新回放现场 6412 帧：首次暂停发生在源时间空档，最终主图未恢复。它与原现场首次暂停的帧不完全相同，不能把单次回放当作现场逐帧确定性复现。全部已录帧处理和保存成功不代表传感器采集连续，已存在的约 14 秒空档不能由慢放补回。

候选 2 的 1581 帧无 Tag 回放，前 40 秒预先限定的普通运动段达到 85 个主图节点、仍可写主图，切链数只有初始化时的 1 次；全段完成输入处理、保存和数据库检查，失锁后纯视觉合并仍未通过。此失败保留，不能用同一录像启用 Tag 后的成功替代。

数据 fsync 本身仍可能阻塞。本次改动减少冗余持久化工作，并未证明已消除现场长停顿。磁盘独立回放没有真实 ZED/SVO/建图并发竞争，不能代替现场连续采集验收。未采用 `sync_file_range` 作为持久化替代：该调用不保证元数据和磁盘缓存持久化，且 WRITE 模式仍可能阻塞（[Linux 接口文档](https://man7.org/linux/man-pages/man2/sync_file_range.2.html)）。

异步持久化没有提前宣称数据已安全落盘。断电时未持久化段、当前打开段以及帧队列都可能丢失；正常退出会全部排空并核验。512 MiB 是已关闭待同步文件的总字节上限，不是内核页缓存或全部进程内存上限。文件 `write`/`flush`、同盘 SVO 和内核写回仍可能阻塞，因此该改动只能隔离单个 fsync 的直接串行等待，不能代替后续实机验证。

## 验证记录

- Jetson 候选 2 相机、工作进程原生编译、依赖解析和 SDK 内私有 ZSTD 符号测试通过。
- 相机 15 项 CTest 通过，包括逐阶段中断提交测试、所有帧有序关闭和最终状态持久化；这些不是断电硬件试验。
- 候选 3 相机 16 项 CTest 通过，新增持久化线程阻塞时超过 64 帧仍可采集、按序逐字节排空、字节容量包含正在同步段、磁盘错误唤醒等待者和完整 Writer 失败收尾检查。
- 连续性状态机测试通过：正常质量但非恢复级质量可以续建；同样的证据不能初始化、绕过失锁恢复、接受旧帧或错误坐标系。
- 状态显示 6 项 Python 测试通过。
- 第一轮原生视觉事务测试因测试脚本遗漏私有 trace 目录而未运行成功；保留该失败记录，第二轮补齐测试环境后运行，未修改 Core 或质量门槛。
- 写盘基线与候选的固定顺序单次对照、完整回执和剩余问题见本轮诊断包；现场连续运动、长时采集和无 Tag 失锁后续建尚未验收。

候选 2 的无注入写盘测试：同一 64.9473 秒、1581 帧输入，两次总封存时间分别为 65.0541 / 65.0526 秒，均逐字节一致且无超过 300 毫秒的采样延迟。**其中标为 baseline 的编译并未使用旧版头文件，不能作为基线对照。** 原因是 `pace_rgbd_spool_writer.cpp` 与候选 `rgbd_spool.hpp` 同目录，带引号的 include 优先于 `-I`。候选 3 初次标为 baseline 的注入试验也受此影响，全部原始记录保留并作废其“基线”身份。

修正后的基线将同一测试源复制到无任何头文件的独立目录，保存编译器 `-MM` 依赖路径。`round6_baseline4` 在运行前的来源校验中停止：当前 8 号的精确相机源码与仓库根目录相比，只有读取帧时是否复制字符串的区别。经 `provenance/production8-20261019/camera6-build-source.zip` 核对，实际部署头文件 SHA-256 为 `2bfff51646703da618e59600b41fa7d332d9505133bfddf5368acd4f20c55f78`。`round6_baseline5` 按该精确来源做一次真正旧版基线，比较对象固定为 `round6_validation3/paced_candidate_stall`，不择优选取重复结果。两者都给第 8 段注入一次 14 秒 fsync 等待；注入库只用于离线测试，不进入相机运行环境。

候选包首次 check-only 发现新增测试文件在生成清单后才被复制，文件哈希不一致，启动被阻止。已将文件复制前移、重新生成清单并保留原失败清单；四组共 31 项 Python 测试和修正后的 check-only 通过。无 Tag 实机候选明确关闭 Tag 检测模块，避免可见标签意外掩盖视觉路径的问题。

## 无 Tag 实机 v2：显示、保存通过，移动连续性失败

实际运行 `continuous_20261012_051722_1055871` 使用独立 `mapping_round6_candidate3_notags_v2`，Tag 检测模块关闭，助手没有发送运动指令。Jetson 系统日期落后于工作电脑，因此保留设备原始时间，并用单调时钟核对事件，不能按目录日期误认成旧实验。

- 18.48 秒完成启动。30 秒订阅收到 590 条持续变化的 RGB 和 27 条主图点云；截图确认 RGB、点云、三轴位姿及建图状态实际可见。
- 操作员按提示完成普通平移和抬头，未要求 Tag、遮挡或返回原视角。
- 首次切链为 `unverified measurement gap`，该帧仍有 190/244 内点/匹配，正常及恢复级几何均合格。不能把这次首次中断归因于缺 Tag 或低特征质量。随后还发生真实里程计失锁；不能把所有后续切链都归结为同一个原因。
- 采集源跨度 302.686 秒，共 6,480 帧，出现 5 次超过 300 ms 的空档，最长 29,915.284 ms。5 次生产者等待累计 55.949 秒，最大 29,862.9 ms。待持久化队列峰值 532,977,710 字节，接近 536,870,912 字节上限。
- 最慢数据 fsync 为 32,744.1 ms，所在段总提交耗时 40,067.3 ms；该段线程 CPU 约 8.1 ms、运行队列等待约 1.7 ms，不能解释成线程一直得不到 CPU。
- 同次运行的内核日志在单调时钟 `532272.477` 秒记录三条 `nvme nvme0: I/O ... timeout, aborting`，随后三条 abort 完成。开始单调时钟为 `532102.591` 秒。这是存储设备/链路超时的直接证据，不只是应用层慢计算。
- 只读 SMART 查询成功，保留原始值。`media_errors=2`、非零历史温度/热管理计数属于累计记录；没有测试前基线，不能把它们全部归因于本次测试，也不能仅据此判定散热、供电、驱动或介质中的哪一项为根因。`critical_warning=0` 和空错误页也不能否定内核本次超时。
- 退出码为 0，所有子进程正常结束，UDP3333 已释放。235 段全部排空，6,480 个源时间戳在采集台账、spool、处理台账及 SVO 核验中逐项一致；保存文件 SHA-256 和关闭后的 SQLite `quick_check` 均通过。提前一次审计因进程尚未关闭而在入口断言退出，没有读取活动数据库；关闭后才完成审计。
- 最终主图仅 1 个节点、3,638 点，13 次切链（含初始化）、0 次恢复。首次断开前主图仍只有一个参考节点，现有三候选纯视觉恢复无法据此完成合并。**完整保存已采帧不等于采集完整，更不等于连续建图成功。**

因此候选没有替换 8 号，现场验收失败记录保留。单次 14 秒故障注入的收益仍有效，但不足以处理真实设备的连续慢写和更长超时。不能靠放松质量门、跳帧或继续增大有限队列宣称解决。

本轮完整输入、SVO、数据库、点云及日志备份到用户指定的电脑目录，原设备数据保留。后续先定位存储设备/链路超时，再验证采集连续性；无 Tag 时参考不足及视觉恢复失败仍是独立待解决项。不要把“旧关键帧通道存在”写成“无 Tag 场景已可用”。
