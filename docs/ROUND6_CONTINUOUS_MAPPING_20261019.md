# 无 Tag 连续建图：候选修复与验证边界

用户本轮澄清的目标是减少无 Tag 建图过程中的中断，不是要求操作员等停图后再找 Tag。当前生产 8 号仍为 `mapping_combo42_camera6`；本轮修改在 `codex/round6-capture-recovery` 和独立 Jetson 候选环境，尚未部署。

## 已修改

1. **正常续建不再额外套用恢复门槛。** `DeferredMappingSession` 原先无论是否已获准写主图，都先调用 `localGeometryReady()`。后者要求恢复级证据，包括更高的内点比例；正常质量已合格的帧也可能被挡住。新增 `frameProcessingReady()`：同一已注册坐标系、主图写入授权仍有效时，使用正常质量要求；初始化、暂停、丢失、过期、坐标系改变仍走原有恢复检查。未降低正常质量、恢复质量、几何验收、点云密度或处理帧数。
2. **减少录制段的重复同步。** 每段保留数据文件 fsync、回执文件 fsync、覆盖两次重命名的一次目录 fsync。正在录制的进度状态在上述三步成功后原子替换，不再额外 fsync 文件和目录；启动、最终关闭、失败状态仍持久化。每段同步调用从 5 次降到 3 次。未改成超时丢帧，也未增加队列容量。
3. **记录直接可查的停止原因。** `frames.csv` 增加完整 `quality_reason` 及运动、尺寸、协方差、视觉、深度、恢复级质量字段。状态 JSON 保留当前和最近失败的质量证据、两条恢复通道各自的理由、旧帧配准计数和对应源时间。
4. **区分无 Tag 与不能建图。** HUD 显示主图 Tag 数为 0 时仍可尝试旧关键帧恢复；检测数不等于绑定数，绑定节点数不等于独立参考数。显示所有已验证 Tag 参考数，未核验的数据不冒充零。正常建图不要求 Tag；Tag 通道失败后依然尝试原有纯视觉通道。
5. **区分文件同步与线程调度。** 每段 `seal_latency.jsonl` 分别记录 flush、数据 fsync、重命名、回执写入/fsync、目录 fsync，以及队列积压、生产者等待、写线程 CPU/运行队列等待、Dirty/Writeback。设备没有 `/proc/pressure/io` 时明确标记 unavailable，不把缺失解释成无 I/O 压力。
6. **将逐帧写文件与段持久化分到两个线程。** 候选 3 中，前者继续按源时间顺序压缩、写入 `.partial` 文件，后者串行完成数据/回执/目录同步；只有完成持久化后才提升 `sealed_segments`。待持久化队列只存路径对应的段元数据，同时限制为 32 段、512 MiB（包含正在同步的段），原始帧队列仍为 64 帧。最终关闭必须排空两个线程；任何错误都保留未完成数据并报告失败。超过容量仍会施加反压，不承诺任意长磁盘故障下无损且永不阻塞。

## 当前证据与限制

正常续建的额外拦截由状态机回归复现并验证修复。但第一版三组完整录像回放中，没有发现 `main_write=1, usable=1, recovery_geometry=0` 的帧；**不能把这一修复说成此前现场停图的已证实主因**。

本轮重新回放现场 6412 帧：首次暂停发生在源时间空档，最终主图未恢复。它与原现场首次暂停的帧不完全相同，不能把单次回放当作现场逐帧确定性复现。全部已录帧处理和保存成功不代表传感器采集连续，已存在的约 14 秒空档不能由慢放补回。

候选 2 的 1581 帧无 Tag 回放，前 40 秒预先限定的普通运动段达到 85 个主图节点、仍可写主图，切链数只有初始化时的 1 次；全段完成输入处理、保存和数据库检查，失锁后纯视觉合并仍未通过。此失败保留，不能用同一录像启用 Tag 后的成功替代。

数据 fsync 本身仍可能阻塞。本次改动减少冗余持久化工作，并未证明已消除现场长停顿。磁盘独立回放没有真实 ZED/SVO/建图并发竞争，不能代替现场连续采集验收。未采用 `sync_file_range` 作为持久化替代：该调用不保证元数据和磁盘缓存持久化，且 WRITE 模式仍可能阻塞（[Linux 接口文档](https://man7.org/linux/man-pages/man2/sync_file_range.2.html)）。

异步持久化没有提前宣称数据已安全落盘。断电时未持久化段、当前打开段以及帧队列都可能丢失；正常退出会全部排空并核验。512 MiB 是已关闭待同步文件的总字节上限，不是内核页缓存或全部进程内存上限。文件 `write`/`flush`、同盘 SVO 和内核写回仍可能阻塞，因此该改动只能隔离单个 fsync 的直接串行等待，不能代替后续实机验证。

## 候选 4：为已测到的同步积压留出有限余量

用实机 v2 的 235 个实际段大小和提交耗时做队列估算，移除已知的五次生产者停顿后，待同步峰值约 1,173,566,455 字节、49 段。这个模型只用于选择有限容量，不会补回采集空档，也不能保证新的并发负载仍有相同的磁盘耗时。

关闭文件的待持久化队列改为最多 128 段、2 GiB；原来的 64 帧图像队列、4 GiB 剩余磁盘检查、逐帧输入、全部 fsync 和质量门保持不变。文件在数据及回执持久化前仍不能对处理器发布，结束时仍须排空。此额度不是预分配 2 GiB 图像内存；但内核脏页和写回仍可能阻塞，持续磁盘故障超过容量后仍会反压，不能据此宣布 NVMe 超时已修复。

Jetson 原生编译、相机 CTest、SDK 符号隔离及门控/质量回归通过。新增确定性试验在持久化线程停住时压入 50 个 24 MiB 的元数据记录；另用 1,500 个微型 RGB-D 帧验证继续采集、未提前发布、源时间/字节一致和结束排空，未实际分配或写入 GB 级测试图像。旧 512 MiB / 32 段头文件运行同一新增测试按预期失败，编译器依赖记录确认它确实使用旧头文件。新版通过不是重复运行直到成功；现场结果单独记录。

候选4实机v3仍失败，不能保留“扩大文件额度就解决”的结论。启动16.78秒，实际RGB/点云/三轴可见；本轮没有收到操作员完成移动的回复。7,533帧、272段完整核对和保存，但出现5个采集空档，最大10.483秒；6次生产者等待，最大10.458秒。待同步文件峰值636,257,056字节，远低于2GiB。现场线程快照中有page wait与journal wait；本轮普通权限dmesg被拒绝，不能据空事件数组判断没有新NVMe超时，也不能把上一轮硬件超时直接套到这次全部等待上。最终主图1节点、6次切链（含初始化）、0恢复。失败数据见[候选4与实机v3证据](../diagnostics/20261019_round6_candidate4/README.md)。

所有建图子进程exit0、SVO核验/保存SHA/closed SQLite检查通过，但外层wrapper返回1。它在遥控退出时发现命令行身份不匹配、PID尚存在便立即报错。事后遥控日志有锁定/灯归零退出提交，PID已消失、UDP3333释放。代码存在cmdline先消失、proc项随后消失的退出时序风险；未采到报错瞬间完整proc状态，不能断言已确认具体瞬时进程状态。

## 候选5：压缩与全部磁盘写入分离

候选4的压缩线程仍直接调用文件write，隔离fsync不足以隔离内核写回等待。候选5只在该线程做无损编码和内存拼段，由一个专用线程完成文件write、flush、fsync、回执及状态写入。

- 压缩段按string容量而非有效字节数计费，含正在写出的段，最多2GiB/128段；释放段内存后才释放队列额度。单段有效载荷最多32MiB，或按原1秒源时间封段，先达到哪个就封段。额外还有一个正在构造的段和单帧编码临时空间。
- 相机前的64帧队列不变。未持久化的压缩RAM是易失数据；原SVO继续录制。持久化条件、最终排空及输入逐帧核验全部保留，失败不能标成完整保存。持续磁盘故障超过有限缓冲仍会反压。
- 新增`data_write_ms`区分实际写文件耗时与fsync耗时；`pending_storage=compressed_ram`、`pending_bytes_accounting=capacity_including_inflight`明确队列含义。
- 原生测试分别阻塞write和fsync，每种1,500帧全部字节一致、没有提前公布未持久化输入；分别注入write/fsync失败，确认不会推进失败段的持久化高水位。相机16项CTest、SDK/门控/质量回归通过。
- 仅对生成的连续入口修正遥控退出观察：身份暂时不匹配时，在原10秒期限内继续只读等待；不向不明身份发送信号。持续不明仍返回2、仍在运行返回1；PID消失后仍核验本次退出回执。独立回归覆盖瞬时、持续不明、仍运行和已退出四种情况。

候选5通过33项Python检查及check-only后启动一次实机v4。68.54秒后因“等待同一遥控控制器灯光就绪超时”退出；本次没有启动相机或建图，没有生成mapping.log，不能称新版RGB/点云/连续采集/保存已通过。最终遥控状态是shutdown、双灯请求0、从未激活运动输出；退出后UDP3333空、没有建图进程。没有重复启动到成功；灯光就绪失败的具体触发项仍需诊断。源码检查已覆盖退出瞬时身份消失，但此轮尚未进入正常建图退出验收。

只读journalctl后续可读取：在field v3结束后、field v4开始前的单调时间535183.581秒又记录一次NVMe timeout/completion polled。它不能直接解释v3期间每次等待或v4就绪失败；存储异常仍待查明。最新构建及启动失败证据见[候选5目录](../diagnostics/20261019_round6_candidate5/README.md)。没有继续整段视频备份；未切换8号，既有8号全部声明哈希再次核对一致。
