# Tag 恢复与逐帧处理速度验证

本轮恢复最新候选的 Tag 识别、参考积累、辅助定位与重定位通路。此前为验证无 Tag 连续建图，候选10入口把 `tag_modules` 置空；相关代码没有删除。候选11重新绑定经过哈希验证的角点观测模块，并在状态面板区分“Tag 已开启”“已关闭”和“状态待确认”。检测数量为零不会再被误当成功能关闭。

Tag 观测仍绑定原始像素、源时间和标定。检测到一个方码不直接授权主图写入；原始深度几何、独立参考、观察期、主图隔离规则均保留。无 Tag 时仍走旧关键帧恢复通路。本轮没有改变点云密度、质量门槛或全帧处理要求，也没有备份视频、删除输入、开启相机或控制推进器。

四组共18,142个处理帧，逐项源时间一致，无跳帧或非法失锁写入。最终点云、帧台账、Tag 导出、数据库哈希及关闭数据库的 `quick_check` 均通过。原始录像状态文件哈希保持不变。

**整体提速尚未证实。** 短片快4.15%，长片慢0.69%；几何结果也不逐位一致，不能只选短片作为提速结论。分歧从第二帧内点数开始，现有 rtflann 随机树内部使用 `std::random_device`，不受 worker 的 `cv::setRNGSeed` 控制。

## 优化范围与原生核验

候选只将 F2M 四个特征循环中重复计算的相机局部逆变换改为本帧按需复用。相机模型在该帧内不变，仍调用原 `Transform::inverse` 与 `transformPoint`，没有改浮点公式、特征、迭代次数、质量条件或图结构。未使用到的空模型或奇异模型不提前求逆。

原生探针对100帧、3个相机的90,000次逆变换与点变换逐位核对通过；两个奇异模型分支均按原设计拒绝。UBSAN通过。4组Core视觉恢复、准备、生命周期、Tag深度回归通过，38项Linux入口/队列/原始像素/显示测试通过。

ASAN并未通过：报告发生在NVIDIA `libnvfnet.so` 退出析构中。仅构造普通CameraModel、完全不执行候选缓存的对照也复现相同错误。失败日志保留，没有抑制该错误或将其算作通过。

独立微基准中重复求逆部分由约68.7毫秒降至4.5毫秒；这只代表该局部运算，不能用作整体建图加速倍数。

额外固定随机诊断只在独立进程中绑定每线程随机序列，使用同样的1,581帧原始输入、已验证Tag观测和原几何规则。两版的 `frames.csv`、`main_cloud.ply`、`tags.json` **逐字节相同**，均99主图节点、102,189点、25切链、1次恢复。旧版87.190秒，新版85.442秒，单次核心处理墙钟快约2.00%；里程计分项仍在61.2秒左右，不能据此宣称稳定的2%全链路加速。这组检验支持缓存改动未改变运算结果，并确认随机过程会影响普通回放比较。诊断插件不安装到候选运行包或8号。

首次固定随机诊断因验证脚本缺少专用trace目录，在2.978秒时拒绝继续。只补齐诊断目录后重新执行固定的一对比较；首次失败保留。没有重复挑选成功的恢复结果。

候选保留这一等价的局部计算优化，整体积压问题仍待继续处理。构建、全部回放、失败记录、运行包绑定与脚本在[本轮诊断目录](../diagnostics/20261019_tag_speed11/README.md)。
