**1. RViz 消失：合法拒绝回执触发恢复进程异常，已经证实。**

v8：`custom_20261009_133832`。完整事务日志有三次 Tag 提案，前两次被同一局部边拒绝，第三次发生版本竞争。此前摘要把它写成“第二个提案”，这里按完整日志纠正。

| 提案 | observer/Core revision | 结果 | 请求到回执 |
| --- | --- | --- | --- |
| 1 | 371 / 371 | 362→363 原始运动与里程计不一致 | 约 436 ms |
| 2 | 400 / 400 | 同一条 362→363 边再次否决 | 约 480 ms |
| 3 | 403 / 404 | 图已更新，拒绝过期提案 | 约 262 ms |

旧 Python 接收器要求 rejected 也必须 Core revision 等于 observer revision，第三条回执触发 `ValueError: terminal graph revision`。恢复消费者退出，启动器按关键进程故障关闭建图及 RViz。地图仍被保存，但退出码 1、cleanup=false。

候选已将已认证、身份一致的 rejected 回执作为终态处理，允许 Core epoch/revision 单调前进；committed/observing 的严格身份及完整边检查保留。16 项接收器回归和原生打包检查通过。v9 没有恢复提案，因此不能说这条修复已在真实失锁恢复中通过。

审查点：`runtime/libexec/wbrov_corner_recovery/bridge_status.py:6`、`live_bridge.py:79`。请核对所有正常拒绝是否均不再成为进程级异常；来源不符、身份冲突仍应明确拒绝。

**2. 有正确候选也恢复不了：当前位置恢复与整个历史子图的准入绑在一起。**

v8 主图确实记住了 Tag 8，恢复也确实生成了三桥提案。第二次三组节点对为 396→303、397→290、398→333；关闭数据库后的双向原始 RGB-D 内点数分别为 151/150、106/111、134/124。

但 `validateRecoveryCache()` 必须先逐边认证当前 epoch 的整个保留序列。最早的 362→363 有 97/55 个双向内点，两方向结果相差 3.18 mm、0.443°；与记录里程计旋转相差 **2.571°**，超过 2° 门限。后续观察再好，还是先被这条旧边否决。

这证明两份运动估计不一致，不证明哪一份是真值；正反配准来自同一对图像，也不是两路独立传感器。不能据此直接用新配准覆盖旧边，或把 2° 调大直到通过。

源码：`recovery_geometry.inc:95`、`:140`，`Rtabmap.cpp:9368`、`:9390`。Core 还要求 `sourceResetEpoch == _resetEpoch`，旧的未注册 epoch 无法经当前事务补合。

已有候选在独立复验确认这种矛盾后撤销局部连续性，由下一条可靠输入创建新隔离段。它能绕开已知坏边，却会丢弃当前恢复积累，需要重新攒参考；它只处理“有效原始配准与旧运动矛盾”这一种拒绝，缺深度、缺邻边、弱配准等不触发它。旧段仍保存但在线不补合。不要把它描述成完整解决方案。

**建议讨论的核心改法**：把两项授权分开。

- **当前重定位**：可靠的主图锚点给出当前位置，经连续观测、几何/重力验证后，只授权从该处开始的新段继续进入主图。
- **历史子图补入**：单独验证历史段，失败就保留为未对齐归档。恢复当前建图不应要求整段历史同时过关。

实现不能只设置 `registered=true`：必须明确切断坏段与新起点的自动邻接、限定注册节点集合、记录新段锚定关系，并验证点云组装和保存不会连带提升旧段。这仍符合“先完成主图恢复；子图互连以后再做”的范围。

**3. 无 Tag 路径还存在候选生命周期问题，词 ID 修复并未解决全部问题。**

v8 原始候选日志已验证：例如 current=385/old=350 的 287 个内点，在求解用 Signature 两侧命中均为 287，在缓存 Signature 两侧命中均为 0。这支持此前词 ID 空间问题及候选修复方向。

但完整 Core 日志同时出现：

```text
local-submap newest bridge is stale (current=394 newest_candidate=395)
visual recovery lacks six independent authenticated image receipts
local-submap newest bridge is stale (current=399 newest_candidate=398)
```

日志中最新候选检查拒绝 5 次，六份 receipt 缺失拒绝 4 次；这些是节流后的日志次数，不是完整尝试数。

候选在 `Rtabmap.cpp:4398` 采集；同次 process 后面的 cleanup/小位移分支会删除临时 Signature，并清除 epoch 索引和 receipt（`:5752`、`:5808`），但没有在这些分支同步移除 `_crossMapLoopEvidence`。Wrapper 在 process 返回后才准备恢复；`visual_recovery.inc:93` 要求候选末帧等于最后工作 Signature，后续还要求六份 receipt。因此可能先缓存到候选，再失去其合法端点，整组三桥被拒绝。

修改方向：只让已经保留、receipt 与 Core 图仍有效的端点进入可提交候选池；删除/合并节点时同步使有关候选失效并补选。也可延后候选接纳到节点保留之后。不能只删 newest 检查或缺 receipt 检查。需要覆盖真实“检索→候选→节点清理→准备事务”的回归；目前合成测试中人工选择候选 ID 的成功路径不能覆盖这一生命周期。

**4. 最新延迟必须拆开解释：1.46 s 含探针延迟，但仍有真实停顿。**

v9：`custom_20261009_142237`，约 20 分钟静止观测。

- 23,000 条 OdomInfo，lost=0；epoch=0、cut_count=0。

- 完整迁移有 17 个暂停时段，18 条过期原因迁移（15 条 source/arrival expired，3 条 stale source，其中一次是在同次暂停中更换原因）。generation 始终为 0，末态 NORMAL，不能按迁移行数计算切链。

同时下一源帧 `1791528106293575000` 的里程计日志 delay=749.192 ms，而运算 update 仅 37.667 ms；再下一帧的采集日志为：

```text

recording_journal_ms=0.032 sdk_recording_status_ms=0.002
low_retrieve_build_publish_ms=2.469 total_ms=686.100
```

原始录制台账也有 683.313 ms 的源帧间隔，故不能把整次停顿都归为探针假象。634.848 ms 位于调度决策至 SDK grab 前，包含计划日志等工作及可能的线程调度停顿，不在刚改成后台的录制台账提交里。另一次 749.961 ms 的里程计源间隔期间，台账仍有相机帧，说明“相机仍采集”与“VO 输入/处理仍连续”也必须分开。

**5. 还未在实机暴露的预算矛盾，作为风险而非已证实主因。**

Core 恢复票据共 6 s（`MappingContinuityGate.h:67`、`:316`）；观察需要五个新的高清建图帧，当前高清输入约 1 Hz，所以五次观察通常占约 4–5 s，而不是状态机注释中的最短 500 ms。准备和最终提交都重新执行整段原始配准与影子优化，耗时随保留段增长；Python 另有 12 s 超时，超时直接抛异常（`live_bridge.py:114`）。

v8 三次提案在准备早期就被拒绝，没有进入五帧观察，不能说它们是上述超时导致。但后续“允许慢处理”方案必须先明确：历史求解预算、观察预算和当前位姿新鲜度各管什么。建议使用冻结的有界候选快照做后台只读求解，最终回串行线程复验身份/端点和当前连续性；不能无限延长旧票据，也不能使用过期位姿驱动实时显示/控制。

**6. Tag、last trusted 与 epoch 日志还有易误判的地方。**

v8 Core 消费者的真实像素绑定：主图 epoch0 的 Tag8 有 50 条，Tag13 有 1 条；私有 epoch1 的 Tag8 有 11 条。Tag13 只有一份旧参考，不能满足当前三视角规则。不能把上一批“主图只有 Tag8”的结论不加条件地套到全部新试验。

旧 `apriltag_keyframe_bindings.jsonl` 使用的 `reset_epoch` 是 binder 自己按 lost 上升沿累计的序号（`src/apriltag/apriltag_keyframe_binder.py:183`），同一次 v8 恢复段记录为 8；Core receipt 的 epoch 却是 1。这两个字段不是同一个计数器。旧 binder 只作为诊断，不是核心事务授权；分析脚本/UI 应明确命名或采用 Core 的统一身份，否则会把一个 Core 子图误解为多个子图。

v9 两路 Tag 日志没有形成有效识别/绑定或提案，不能用它验收 Tag 恢复。主图只有节点 1，静止场景被抑制新增节点是正常行为，不能把数据库中大量中间记录当成主图增长。

`lastTrustedNodeId` 在当前 `validateProposedMapObservation()` 中是可信历史范围的截止标识，实际验证可以匹配多份旧关键帧，不要求每次回到那张 last trusted 图像本身。UI 却只给最后可靠图，容易把人引向单一视角。建议显示“当前候选对应的主图参考、已获得几份有效观察、当前阻塞原因”，并分别显示 Tag 检出、像素绑定、几何通过和 Core 提交，避免“看见 Tag 就应该已恢复”的误解。

**7. 对延迟建图方向的建议，待 Claude 复核。**

保留三条独立进度：实时采集/局部定位、可延迟的主图恢复求解、历史段补入。先持续保存原始观测，后台处理固定快照，界面显示主图处理滞后；新鲜的当前位姿仍由实时链路判断。当前重新锚定成功后继续主图，历史坏段保持隔离，后续两端锚定、重算验证通过才补入。

SVO 已录制，但存的是原始立体数据，不是所有计算深度；SDK 接收计数/闭合索引/首末解码通过也不等于全程逐帧回放或传感器零丢帧。v9 31,271 帧、7.84 GB 归档已保存；延迟队列需要明确容量、磁盘余量和溢出行为，不能无限缓存。
