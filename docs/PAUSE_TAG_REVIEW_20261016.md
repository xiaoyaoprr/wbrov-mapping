# 断图、标签和延迟建图：问题清单与讨论稿

用户要求先讨论、找问题、交叉复审，再一起修改。本次没有改算法、启动器、门槛或部署。此前静止启动、点云显示、正常保存通过，只能说明该测试场景可用，不能证明移动后能连续建图或自动恢复。本次移动序列明确暴露了后者仍不成立。

证据目录：[20261016_pause_and_tags](../diagnostics/20261016_pause_and_tags/README.md)。分析对象是已结束的 `custom_20261009_061136`，不是随后正在运行的新任务。设备文件日期与主机日期不同，未修改时钟。

## 1. 第一次暂停确实经历了短暂退化，后续恢复没有完成

主图最后可信节点为53。第一次记录到弱质量发生于首个数据库节点后约53.68秒，原因 `visual=cells=5<6`；约0.30秒后局部几何恢复，但尚未完成主图观察。约1.783秒后又出现17/112内点、比例0.1518，低于当前0.25条件，切断连续性。后面还有真实 `lost=true`、低覆盖，以及一次1.066417秒源间隔且测量区间为0的中断。不能把这些都称为单帧误判。

当前弱质量等待只解决一部分短暂下降；既没有证明本次5格对应的位姿一定错误，也不能因为 `lost=false` 或内点很多便认定仍可信。还需要用同一录制数据检查支持分布、位姿误差和恢复召回率，不能只做静止45秒验收。

定位：[`MappingContinuityGate.h`](../src/rtabmap_ros/rtabmap_slam/include/rtabmap_slam/MappingContinuityGate.h) 的 `pendingVerificationEligible()`、`observe()`、500毫秒弱质量和6秒总核验预算；[`CoreWrapper.cpp`](../src/rtabmap_ros/rtabmap_slam/src/CoreWrapper.cpp) 的 `mappingEvidence()`。

## 2. 不止检测到一个标签；主图只有一个已绑定的标签 ID

原始像素检测记录包含0、2、8、10、11、12、13。主图 epoch 0 中有4次 Tag 8 的精确节点绑定；其他ID主要出现在未对齐分量。因此“主图只显示一个Tag”不能直接等价于“识别器只能识别一个”。

| --- | --- |
| 0（主图） | 8（4） |
| 1 | 10（2）、0（2）、11（4） |
| 2 | 8（3） |
| 3 | 8（5） |
| 4 | 8（6） |
| 5 | 13（2） |
| 6 | 11（6）、13（2） |
| 7 | 11（3） |
| 8 | 11（1） |
| 9 | 2（1）、12（1） |
| 11 | 2（2）、12（2）、11（3） |

一个从未在主图中建立位置、也没有预先测定坐标的新Tag，只给出相机与该Tag的相对位置，不能单独决定它与主图的变换。多个子图之间共享Tag可以提供候选连接，但要验证实际几何和分量关系。显示层还可能因平面位姿歧义、节点已不在快照、同ID的位置冲突而不放置标记；本统计不是逐时刻RViz标记数的重建。

需要改进的产品表达：分别列出“当前检测到的ID”“在主图有已知位置的ID”“只属于未对齐子图的ID”“本次恢复被哪一项拒绝”，不能只显示暂停或一个标签标记。

## 3. 有一处确定的 Tag 确认频率不匹配

旧 `apriltag_landmark_node.py` 被入口重映射到约1 Hz的建图图像，但默认 `APRILTAG_TRACK_MAX_GAP_S=0.60`、连续3帧确认。间隔超过0.6秒就清空待确认状态，于是大量观测每次重新从第一帧开始。实测CSV中多个ID一直是 `confirming`，这一路 accepted 为0。

未修改的 [`TemporalPoseGuard`](../src/apriltag/detector/tag_pose_guard.py) 做静止有效位姿对照：6次输入，1 Hz接受0次，6 Hz接受4次。见 `tag_cadence_reproduction.json`。这是可复现配置缺陷，不是让操作员多看几秒就必然解决的问题。

但该路径主要影响旧位姿确认/显示；像素绑定、多视角Tag恢复是另一条路径，本次确实已经发起合并。所以不能把它当成“全部恢复失败”的唯一原因。修正时应明确输入节拍及时间预算，保留缺帧、跳变、歧义检查，而非无条件通过单次观测。

## 4. Tag 8 发起过7次恢复，全部在后续验证失败

| 失败类别 | 本轮事实 |
| --- | --- |
| 子图内部配准不足 | 85→86正向/反向分别3/17个内点，要求25。 |
| 留出几何验证 | `leave-one-pair-out gravity-constrained depth-corner alignment failed`。 |
| 事务过期 | `Tag recovery preparation ticket is no longer current`。这说明有失效事件，不等于已证明计算太慢。 |
| 段成熟度 | 3节点、5节点时未通过源时间/实测重力稳定性。 |
| 内部运动不一致 | 102→103原始配准与里程计或邻接边不一致，出现两次。 |

“三视角Tag成功”仍只是候选；实现还验证整个待合并子图的内部RGB-D连续性，再做重力、留出、修正量与提交检查。见 [`recovery_geometry.inc`](../src/rtabmap_core/corelib/src/recovery_geometry.inc) 的分量认证与 [`Rtabmap.cpp`](../src/rtabmap_core/corelib/src/Rtabmap.cpp) 的Tag事务路径。

应讨论：能否只接回具有充分证据的连续片段，隔离损坏前缀/间断，而不是整段任何坏边都阻止后续可靠区域接入。不得把删掉坏边后剩下的不连通部分直接摆到主图，也不能未经验证回填缺口。

此外，普通外观回环有186、239、248等大量二维内点，但候选日志中的有效三维点有0/1个；其他候选也只有少数点。必须继续查深度有效性、存储/坐标对应和筛选范围，现有日志不足以判断是场景测不到深度还是实现/数据表达问题。单纯增加等待时间不会凭空产生缺失的三维证据。

## 5. Last Trusted 是单帧历史参考，不是容易执行的恢复操作

实现只保留最近一张获准写入主图的图像，停写后按状态代数发布。当前参考为节点53，它不一定是最容易认出的场景，也不是最后看清Tag的位置。窗口面板较小，只有一张图，没有沿途缩略图、已知Tag清单或恢复候选进度。要求操作员精确回到该视角不应成为唯一办法。

建议讨论：保留最近一段可信轨迹的若干清晰关键帧，优先显示含已知Tag/明显结构的视图；另列可用于恢复的Tag ID及拒绝原因。主图位置尚不确定时，不给出假装精确的地图方向箭头。缩略图选择需要清晰度与可重识别性评分，不能只取“最后一帧”。

## 6. 保存契约还没有适配“允许未对齐子图”的设计

本轮数据库保留237节点，12个map ID，其中127节点参与可导出的度量图；已保存的全局优化位姿只覆盖主图29节点。中间产物有13,611点，但覆盖核验返回 `complete_saved_graph_but_partial_database`、`publish_allowed=false`，最终 `export_succeeded=false`、退出码1。不能把它叫完整地图保存成功；也不能说所有原始数据都丢了。

建议区分三个结果：原始观测/数据库是否完整保存；注册主图是否成功导出；每个独立子图是否带自身坐标和关系清单保存。允许任务以“已保存、仍有未对齐区域”结束，单独控制能否继续主图，不能给未对齐数据伪造成功合图状态。

本包的PLY只是失败导出的主图部分，供诊断；各子图只附归档位姿快照，没有把它们叠成第二张主图。

## 7. 当前缓存不足以支持用户提出的完整延迟重建

当前是20 Hz左右的里程计流与约1 Hz的高清建图流。恢复消费者有128帧内存缓存，并会淘汰/回收；本轮记录到RGB和CameraInfo各5次容量淘汰。这既不是全程记录，也不能把数据库中的237个已处理节点当成所有沿途观测。没有已实现的全程SVO录制保证。

暂停主图不应阻断原始采集保存。后续设计应在任何建图筛选之前记录双目图像/时间戳/IMU，并单独保存水下标定、外参、SDK版本、深度配置及丢帧记录。若使用SVO，不能把SVO误认为已经保存了计算好的深度和点云；这些需要回放重算，或额外记录RGB-D。参见 [Stereolabs录制说明](https://docs.stereolabs.com/docs/development/zed-sdk/modules/camera/recording)。

## 8. 延迟建图需要时间语义与资源隔离，不能只加大队列

建议的讨论架构：

```text
相机/IMU采集 ──→ 持续记录原始数据、标定和原时间戳
      ├──────→ 实时画面、快速局部定位、当前状态
      └──────→ 有界后台队列 → 历史帧顺序处理 → 验证局部段/Tag连接 → 地图修订
```

实时定位仍要求新鲜，不能把几秒前的历史位姿交给控制或伪装成当前定位。延迟地图明确显示“已处理到哪个源时间、落后多久、哪些分量待对齐”。历史处理使用原始时间戳检查帧间连续性，提交修订时验证图版本和坐标关系；禁止通过重打当前时间戳绕过新鲜度门。

先讨论秒级、有上限的显示延迟，具体预算须测量。若平均处理速度持续低于采集速度，延迟会不断累积；应有关键帧选择、后台吞吐预算、积压报警和任务后继续处理，而非承诺任意运动都只延迟一点。RTAB-Map支持数据库重处理和多会话处理，参见[官方流程](https://github.com/introlab/rtabmap/wiki/Multi-Session-Mapping-with-RTAB-Map-Tango)；这只能说明方案有实现基础，不能证明现有定制程序已经具备它。

## 9. 其他已见问题与尚未证实的原因

- 退出阶段状态面板出现 `publisher's context is invalid`，旧Tag节点有 `ExternalShutdownException`。需要核对退出顺序和异常处理；现有记录不能断定它们是停机原因还是停机后的竞态。
- 静止截图已显示固定状态面板细字太小；应改善布局和恢复诊断，而不是把所有信息继续塞到三维原点附近。
- 本轮有一笔事务过期和后续数据间隔中断；需要进一步分解前端处理、发布、回调排队与验证耗时。不能把RTAB-Map日志总delay直接当成纯网络延迟。
- 首次候选测试的GLX黑屏是另一个已知问题；此次暂停证据不能证明它再次发生，也不能宣布此前问题根治。
